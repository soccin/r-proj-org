# R/Tidyverse Analysis Project Organization

## The Core Insight: Data Has a Lifecycle

Raw data flows through transformation stages, and your directory structure should mirror that flow. The key distinction is **provenance**:

- `/data` — things that came from *outside* your project (never regenerated by your scripts)
- `/output` or `/results` — things your scripts *produce*

But that binary is too coarse for multi-stage pipelines.

---

## Recommended Structure

```
project/
├── .here               # Anchors here::here() — or a .Rproj file
├── .gitignore
├── run_all.R           # Sources scripts in order — the pipeline entry point
│
├── data/               # Immutable inputs — never written by scripts
│   ├── raw/            # Exactly as received (downloaded, shared, etc.)
│   │   └── MANIFEST.tsv    # Provenance: name, size, md5, source, date
│   └── external/       # Reference data (gene lists, annotations, etc.)
│
├── cache/              # Intermediate computed files — safe to delete & regenerate
│   ├── 01_tidy/        # Output of cleaning/tidying scripts
│   ├── 02_processed/   # Merged, normalized, feature-engineered data
│   └── 03_filtered/    # Analysis-ready subsets
│
├── results/            # Final outputs — figures, tables, reports
│   ├── figures/
│   └── tables/
│
├── R/                  # Reusable functions (not scripts)
│
└── scripts/            # Analysis scripts, numbered by pipeline stage
    ├── 00_fetch_data.R # Reproduces data/raw/ from its sources
    ├── 01_tidy_input.R
    ├── 02_process.R
    └── 03_analyze.R
```

---

## The Principles Behind This

**1. Number the pipeline stages.** Scripts and their output directories share a prefix (`01_`, `02_`). Six months later, you know exactly which script produced which file without reading anything.

**2. `cache/` signals intent.** The name tells you and collaborators: *this is derived, not precious, can be regenerated.* Add `cache/` to `.gitignore`. `data/` is the opposite case — see the `.gitignore` split below for what to commit outright and what to reference by manifest.

**3. `data/` is read-only.** Scripts never write to `data/` — not once, not "just this one file." Everything else reads from wherever it needs (usually the previous stage's `cache/` directory) and writes only to `cache/` or `results/`. This prevents accidentally overwriting source data and keeps the data flow auditable.

**4. Each script has one job.** `01_tidy_input.R` reads from `data/raw/`, writes to `cache/01_tidy/`. `02_process.R` reads from `cache/01_tidy/`, writes to `cache/02_processed/`. The dependency graph is visible in the file names.

## In Practice (R/tidyverse)

`here::here()` resolves paths against the project root, which it locates by searching upward for an anchor file. If you use RStudio projects, the `.Rproj` file is that anchor and there is nothing to do. Otherwise run `here::set_here()` once, which writes an empty `.here` file at the root. Without an anchor, `here()` falls back to the working directory and every path in the project silently resolves somewhere else — worth setting up first, since everything below depends on it.

Define paths at the top of each script using `here::here()` so they work regardless of working directory:

```r
library(here)

# Inputs
input_dir  <- here("data", "raw")
ref_dir    <- here("data", "external")

# Outputs
out_dir    <- here("cache", "01_tidy")
fs::dir_create(out_dir)   # safe no-op if it exists

# Read
raw <- read_csv(fs::path(input_dir, "samples.csv"), show_col_types = FALSE)

# ... transform ...

# Write
write_rds(tidy_data, fs::path(out_dir, "samples_tidy.rds"), compress = "gz")
```

Use `here()` once per path, to build the directory from the project root, then `fs::path()` to join filenames onto it. Passing an already-absolute path back through `here()` happens to work, but it reads as though the path is being re-anchored when it isn't.

Using `.rds` for intermediate files is better than `.csv` for most cases — it preserves types (factors, dates, list columns) exactly and is faster to read/write. Note that `readr::write_rds()` defaults to `compress = "none"`, unlike base `saveRDS()`, which gzips by default — set it explicitly or intermediates land several times larger than expected.

## Running the Pipeline

The numbered filenames *document* the execution order. `run_all.R` *enforces* it:

```r
# run_all.R
library(here)

# source(here("scripts", "00_fetch_data.R"))   # run once — populates data/raw/

source(here("scripts", "01_tidy_input.R"))
source(here("scripts", "02_process.R"))
source(here("scripts", "03_analyze.R"))
```

Run it with `Rscript run_all.R` from anywhere in the project. Keeping this file working is the cheapest reproducibility check available: if it does not run end to end in a fresh session, the project is not reproducible, whatever the directory structure suggests.

## The `.gitignore` Split

```
# .gitignore
cache/            # derived — regenerate from scripts
results/figures/  # often large — regenerate from scripts

# Raw data: ignore the bytes, commit the provenance
data/raw/*
!data/raw/MANIFEST.tsv

# NOT ignored:
# data/external/  <- reference files are usually small; commit them
# results/tables/ <- often small, useful to track changes over time
```

Large inputs — FASTQs, BAMs, count matrices — have to stay out of git. History is append-only, so a single accidental multi-gigabyte commit permanently inflates every future clone, and deleting the file later does not undo it.

Ignoring the bytes does not mean giving up the guarantee. Commit two small things instead:

- **`data/raw/MANIFEST.tsv`** — one row per file: name, size, md5, source (URL or accession), date received.
- **`scripts/00_fetch_data.R`** — the code that rebuilds `data/raw/` from those sources.

Together they run to a few kilobytes and reconstruct the input state exactly, which is what committing the files was meant to buy in the first place.

Small inputs are the exception worth naming: a 200-row gene list, a sample sheet, a config table all belong in git directly. The rule is about size, not about which directory a file lives in.

---

## Why Not Just `/data/raw` and `/data/processed`?

The `data/processed` pattern is common but has two problems:

1. It conflates the immutability guarantee of `data/` — newcomers (or future-you) don't know what's safe to delete.
2. It doesn't scale past two stages; you end up with `data/processed_v2/` or timestamped names.

The numbered `cache/` stages scale to any depth and remain self-documenting.
