# R/Tidyverse Analysis Project Organization

## The Core Insight: Data Has a Lifecycle

Raw data flows through transformation stages, and your directory structure should mirror that flow. The key distinction is **provenance**:

- `/data` — things that came from *outside* your project (never regenerated by your scripts)
- `/output` or `/results` — things your scripts *produce*

But that binary is too coarse for multi-stage pipelines.

---

## Recommended Structure

```
project/
├── data/               # Immutable inputs — never written by scripts
│   ├── raw/            # Exactly as received (downloaded, shared, etc.)
│   └── external/       # Reference data (gene lists, annotations, etc.)
│
├── cache/              # Intermediate computed files — safe to delete & regenerate
│   ├── 01_tidy/        # Output of cleaning/tidying scripts
│   ├── 02_processed/   # Merged, normalized, feature-engineered data
│   └── 03_filtered/    # Analysis-ready subsets
│
├── results/            # Final outputs — figures, tables, reports
│   ├── figures/
│   └── tables/
│
├── R/                  # Reusable functions (not scripts)
│
└── scripts/            # Analysis scripts, numbered by pipeline stage
    ├── 01_tidy_input.R
    ├── 02_process.R
    └── 03_analyze.R
```

---

## The Principles Behind This

**1. Number the pipeline stages.** Scripts and their output directories share a prefix (`01_`, `02_`). Six months later, you know exactly which script produced which file without reading anything.

**2. `cache/` signals intent.** The name tells you and collaborators: *this is derived, not precious, can be regenerated.* Add `cache/` to `.gitignore`. Never add `data/raw/` to `.gitignore`.

**3. Separate read-only from write-enabled directories.** Scripts should *only read* from `data/`, *only write* to `cache/` or `results/`. This prevents accidentally overwriting source data and makes the data flow auditable.

**4. Each script has one job.** `01_tidy_input.R` reads from `data/raw/`, writes to `cache/01_tidy/`. `02_process.R` reads from `cache/01_tidy/`, writes to `cache/02_processed/`. The dependency graph is visible in the file names.

## In Practice (R/tidyverse)

Define paths at the top of each script using `here::here()` so they work regardless of working directory:

```r
library(here)

# Inputs
input_dir  <- here("data", "raw")
ref_dir    <- here("data", "external")

# Outputs
out_dir    <- here("cache", "01_tidy")
fs::dir_create(out_dir)   # safe no-op if it exists

# Read
raw <- read_csv(here(input_dir, "samples.csv"), show_col_types = FALSE)

# ... transform ...

# Write
write_rds(tidy_data, here(out_dir, "samples_tidy.rds"))
```

Using `.rds` for intermediate files is better than `.csv` for most cases — it preserves types (factors, dates, list columns) exactly and is faster to read/write.

## The `.gitignore` Split

```
# .gitignore
cache/            # derived — regenerate from scripts
results/figures/  # often large — regenerate from scripts

# NOT ignored:
# data/           <- precious, version-control or document provenance
# results/tables/ <- often small, useful to track changes over time
```

---

## Why Not Just `/data/raw` and `/data/processed`?

The `data/processed` pattern is common but has two problems:

1. It conflates the immutability guarantee of `data/` — newcomers (or future-you) don't know what's safe to delete.
2. It doesn't scale past two stages; you end up with `data/processed_v2/` or timestamped names.

The numbered `cache/` stages scale to any depth and remain self-documenting.
